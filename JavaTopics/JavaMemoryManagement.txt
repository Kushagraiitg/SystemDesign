JVM
	- avoids manual memory handling
	- uses garbage collection to remove unused objects
	- divides memory into different runtimes for efficient execution
JVM Memory Structure
	- Class Loader
		dynamically loads .class java file into JVM memory,
		converting bytecode to JVM understandable
	- JVM Memory Area
		Method Area
			created at JVM start
			stores the class level info like metadata, methods and static variables
			shared across all threads
		Heap Memory
			stores objects and instance variables, shared by all threads in app
			GC cleans unused objects from heap
		JVM stacks
			each thread has its own stack
			contains local variables, methods calls and partial results
			release post execution
		PC registers- Program Courier Registers
			particular to thread, contains address of currently executing instructions
		native method stacks
			native lib functions stacks like C/CPP
- Execution Engine
	execute bytecode, converting it to machine level instructions
	includes Interpreter and JIT Compiler
- Native Method Interface
	bridge b/w java code and native apps
- Native Method libs
	contains native libs
	used by interface to execute
	
	
Java Memory Model
	- registers and CPU caches over RAM
	- Visibility - when changed by one, when does the other thread see it
	- Instruction Reordering - reorder by compiler/CPU/JVM
	- JMM defines 'happens-before' relationship
	- memory barriers used
	- volatile: dont cache the variable and dont reorder instructions around it
		- visibility, no atomicity, 
		- count++ is a three step process, overwrite allowed
		- useful when state flag, changed by one thread and others react
	- synchronized
		- visibility and atomicity
		- get lock-flush CPU cache-read from main memory-when exit then write to main memory
		- only one thread can execute at a time
		- when multiple lines need to run together
	- final
		- once contructor completes running, visibility is guranteed to all threads
		- thread safe DTO
